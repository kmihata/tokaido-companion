# Data schemas

Two layers. Public data ships in the repository and is precached. Private data
never enters the repository and lives only in IndexedDB on the device.

Runtime validation is in `src/data/schemas.ts` (public) and
`src/data/privateSchema.ts` (private). Those files are the authority; this
document explains them.

## Provenance fields — on every public record

Carried by stations, waypoints, the route feature, and Hiroshige records.

| Field | Values | Meaning |
| --- | --- | --- |
| `source` | free text | Where the record came from |
| `confidence` | `demonstration` \| `low` \| `medium` \| `high` \| `verified` | How much the content is worth |
| `verification` | `unverified` \| `desk-checked` \| `field-checked` | How it was checked |
| `lastChecked` | ISO date or `null` | When, for things that expire — trail notices, timetables |
| `classification` | `public` \| `private` | Whether it may be in this repository |

Everything in this build is `demonstration` / `unverified` / `lastChecked: null`.
`tests/unit/fixtures.test.ts` asserts that, so the day a record is upgraded, the
upgrade is deliberate.

The reason this exists: a number without its provenance gets reasoned from — by a
tired person at dusk, or by an AI handed the context packet — as though it were
surveyed. The confidence travels with the fact into the packet for the same
reason.

## Public files

All under `public/data/`, generated by `scripts/build-fixtures.mjs`.

### `index.json` — dataset manifest

`dataVersion`, `generated`, `demonstration`, `navigational`, `notice`,
`generatedBy`, and a `files[]` list with byte sizes. The app shows `dataVersion`
in the status strip and the offline screen; it is how Kevin can tell at a glance
which dataset the phone is holding.

### `trip.json` — the container

Fixed dates (`departSeattle` … `returnDate`), day counts, the working route range
(500–525 km), the nominal historical distance (495.5 km), timezone, and the
`notice` string. Sourced from `STATUS.md`.

### `days.json` — day cards

`schemaVersion`, `dataVersion`, `demonstration`, `navigational`, `days[]`.

`tests/unit/schemas.test.ts` asserts every id reference resolves, the dates are
ordered and unique, and the fifteen walking days are numbered consecutively.

### `stations.json` — traditional post stations

A deliberate **subset**, marked `complete: false`. Building the full fifty-three
station ledger — with surviving remnants, visibility, and include/skip decisions —
is separate work and an explicit non-goal for this build.

`id`, `number` (null at the two termini), `name`, `modern`, `lat`, `lon`, `kind`,
`notes`, `visibility`, plus provenance.

Since 2026-08-20, `anchorId` and `positionSource` say where the coordinate came
from. 29 of 31 stations now sit on **real positions taken from the imported
route**; only Kawasaki-juku (unlabelled upstream) and Sanjo Ohashi (past the end
of the source data) remain hand-written estimates, and they say so. The same two
fields appear on waypoints, where ten are now real and the rest — every rail
station, every hazard the route does not pass through, all lodging — are still
estimates.

### `waypoints.geojson` — operational features

A `FeatureCollection` of `Point` features. Properties:

`id`, `type`, `title`, `dayIds[]`, `operationalNotes`, `historicalNotes`,
`safetyNotes`, `links[]` (`{label, url}`), `navigational: false`,
`demonstration`, `anchorId`, `positionSource`, plus provenance.

`type` is one of: `day-start`, `day-end`, `rail-bailout`, `hazard`, `water`,
`food`, `resupply`, `research`, `hiroshige-viewpoint`, `hotel`, `river-crossing`,
`ferry-gap`, `pass`, `tunnel`, `bridge`, `category-change`.

`category-change` is for sites where the road survives by changing what it is —
the Meiji Utsunoya tunnel is the type case.

Hotels in this build are **fictional placeholders**, named as such in both title
and notes, and asserted by test. Real lodging is private data.

### The route files — `route-meta.json`, `route.geojson`, `anchors.geojson`

*Replaced the schematic corridor sketch on 2026-08-20. Generated by
`scripts/import-kaidotrail.mjs` from a preserved source file; run
`npm run route:import` before `npm run fixtures`.*

**`route-meta.json`** is the project container: schema and data version, source
and licence, an ordered list of **paths**, a list of **variants**, totals, and
the outstanding work. It holds no geometry.

| Path field | Meaning |
| --- | --- |
| `id`, `order` | Stable id, position in the route |
| `kind` | `walking` · `transit` · `ferry-gap` · `unresolved` · `excluded` · `connector` |
| `lengthKm` | `null` for a gap — a gap has no length because it has no geometry |
| `startAnchorId`, `endAnchorId` | Named ends, not raw coordinates |
| `note` | Why this path is what it is |
| `resolvedByVariantId` | The variant that closes this gap when active |

| Variant field | Meaning |
| --- | --- |
| `divergeAnchorId`, `rejoinAnchorId` | Where it leaves and rejoins |
| `replacesPathId` | The gap or stretch it stands in for |
| `active` | Only one alignment is walked; the others stay available |
| `rationale` | Why it exists — read by a person, not code |

**`route.geojson`** is a `FeatureCollection` of `LineString`s, one per path with
geometry and one per variant. Properties carry `featureRole` (`path` |
`variant`), `kind`, `lengthKm`, the anchor ids, and full provenance. **Gaps have
no feature.** That is the point: the file cannot draw a line across the Seven-ri
crossing because there is nothing to draw.

**`anchors.geojson`** is a `FeatureCollection` of `Point`s — the named handles
the whole model hangs off. 98 of them came with the source route: post stations,
bridges, passes, checkpoints, junctions, ferry sites.

| Anchor field | Meaning |
| --- | --- |
| `titleJa`, `title`, `romanised` | Japanese label as written upstream, English where a confident reading was available, and whether it was |
| `kind` | `post-station` · `landmark` · `bridge` · `pass` · `checkpoint` · `rail` · `junction` · `ferry-site` |
| `stationNumber` | Traditional Tokaido number, 1–53, or `null` |
| `nakasendoNumber` | Set where the source switches numbering after the confluence — Kusatsu is Tokaido 52 and Nakasendo 68 |
| `pathId`, `indexOnPath` | Which line it sits on and where |
| **`alongKm`** | **Distance from the start of its path. This is the linear-referencing handle everything else measures against.** |

### Assembling the active route

`buildStretches(meta, features, anchors)` in `src/data/load.ts` returns
`{ stretches, breaks }`. A **stretch** is a continuous walkable line with its
own cumulative-distance array; a **break** is a gap no active variant resolves.

Rules it implements, each with a test in `tests/unit/routeModel.test.ts`:

1. Walking paths contribute their geometry, in `order`.
2. A gap contributes its resolving variant's geometry when that variant is
   active, and otherwise ends the current stretch and records a break.
3. If an active variant diverges from a path **before that path ends**, the path
   is truncated at the divergence anchor. The Saya Kaido leaves the east route
   ten points short of the Miya ferry landing, so the spur to the landing is not
   walked.
4. Shared vertices where two members meet are not duplicated.

Deactivating the Saya variant must produce two stretches and a break, never one
line across the bay. That is asserted directly.

### `hiroshige.json` — image metadata, no images

`id`, `stationId`, `title`, `series`, `artist`, `institution`, `sourceUrl`,
`rightsStatus`, `imageAvailableOffline`, `orientation`, `viewpointLat/Lon`,
`viewpointConfidence`, `notes`, plus provenance.

Rules enforced by test:

- `rightsStatus` is `unverified` for every record. No image may be displayed,
  bundled, or cached until it is `public-domain` or `licensed` **for that
  specific reproduction from that specific institution**.
- `viewpointConfidence` is `unknown` and both viewpoint coordinates are null.
  Hiroshige composed, compressed, moved and symbolised. Claiming an exact
  standing position for a staged print would be inventing evidence. The useful
  field question is what he may have been looking at, what he made visible, and
  what can be seen from there now.
- No image files exist anywhere under `public/`.

## Private data

Documented in full in `PRIVACY-AND-THREAT-MODEL.md`. Format summary:

```json
{
  "schemaVersion": 1,
  "kind": "tokaido-private-data",
  "label": "...",
  "generated": "ISO timestamp",
  "lodging": [{ "id", "dayId", "name", "address", "checkIn", "checkOut",
                "lat", "lon", "cancellationDeadline", "notes" }],
  "transport": [{ "id", "dayId", "description", "departsIso", "notes" }],
  "contacts": [{ "id", "label", "detail", "notes" }],
  "health":   [{ "id", "label", "detail" }],
  "notes":    [{ "id", "dayId", "title", "body" }]
}
```

The importer is **strict**: an unrecognised key is a refusal, not a warning. A
file with unexpected structure is more likely the wrong file than a newer one,
and silently storing the wrong file on a phone is the failure worth preventing.

It also refuses: files over 2 MB, non-JSON, non-objects, the public demonstration
dataset (an easy file to pick by mistake), any GeoJSON, a missing or wrong
`kind`, and any `schemaVersion` this build does not implement. Twenty-four tests
in `tests/unit/privateImport.test.ts` cover these paths.

The shipped example at `examples/private-data.example.json` carries a `_readme`
key, so it is **refused as-is**. Removing that key is a deliberate act that
forces a look at the file before it reaches the device.

## Day plan — device-local

Kevin's day-boundary decisions, in IndexedDB under `dayplan.v1`. The route
ships in the repository; this is the delta on top.

```json
{
  "schemaVersion": 1,
  "updatedAt": "ISO timestamp",
  "overrides": {
    "d-2026-10-25": { "endAlongKm": 152.4, "endAnchorId": "a-030",
                      "continueToAlongKm": 161.2, "continueToAnchorId": "a-032" }
  }
}
```

**Only moved days are stored.** Everything else is derived from
`buildDefaultDayPlans()`, which maps the stage endpoints in
`DAILY-SCHEDULE-DRAFT.md` onto route anchors. A change to the route flows
through to untouched days automatically.

Snapshots live under `dayplan.snapshots.v1` — the last 20, each with a label,
timestamp, and the route data version it was taken against, so a restore can
warn that the route has moved underneath it.

## Prepared days — device-local

Under `prepared.v1`, keyed by day id:

```
dayId, preparedAt, checklist { … }, routeDataVersion, activeKm, continueKm
```

Every checklist item is **user-confirmed**. Samwise has no integration with
Footpath, the Watch, or Apple Maps and cannot verify any of them; a tick records
Kevin's own check and the UI says so. `activeKm` is stored so the screen can
notice the day has changed since it was marked prepared and say the export is
stale.

## Day plan export

Written by More → Settings → Export the day plan.

```
schemaVersion, kind: 'samwise-day-plan', exported, routeDataVersion,
overrides: { [dayId]: Partial<DayPlan> },
days: [{ dayId, date, label, startKm, endKm, distanceKm, finishesAt, moved }]
```

`overrides` is what restores the plan, and only holds days actually moved by
hand — everything else follows the defaults for whatever route is shipped, so a
retrace flows through instead of freezing a stale distance. `days` is the
resolved plan for reading, and carries `routeDataVersion` because every retrace
lengthens the route and pushes the later boundaries forward: without it, a plan
exported two versions ago is indistinguishable from a current one, and hotels
are booked against these numbers.

## Anchor adjustments — device-local

Anchor positions Kevin has corrected, in IndexedDB under `anchoradjust.v1`.

```
schemaVersion, anchorId, position: [lon, lat], movedKm, note, savedAt
```

Layered onto the shipped anchors by `applyAnchorAdjustments()`, which changes
only the geometry and the stored `alongKm`. The shipped anchor is never
rewritten, so removing an adjustment restores the published position exactly.
The moved anchor's `source` gains "— position adjusted on device" and its
`verification` becomes `manually-traced`, so an export cannot claim source
provenance for a position the source did not publish.

`note` is required. An anchor found sitting somewhere other than where the
source put it, with no reason recorded, is indistinguishable from a data error.

Refused, by `validateAnchorAdjustment()`: anchors the route model is pinned to
(path ends, variant diverge and rejoin, and any anchor sitting on the same
join); any move that would carry an anchor past its neighbour along the route;
and any move over 500 m.

## Route edits — device-local

Changes to the route, in IndexedDB under `routeedits.v1`.

```
schemaVersion, id, createdAt,
kind: 'replace-section' | 'resolve-gap' | 'add-variant',
label, reason,
origin: { filename, trackName, format, importedAt },
divergeAnchorId, rejoinAnchorId | null, replacesPathId | null,
geometry, lengthKm, active, verification
```

**Every edit is a variant**, layered on the shipped route by
`applyRouteEdits()`. No path geometry is spliced, so no anchor is reindexed and
the imported source stays comparable. `rejoinAnchorId: null` means the edit runs
on to the end — which is how the missing Kyoto approach is added.

Exported as `{ kind: 'samwise-route-edits', appliesToRouteDataVersion, edits }`.
`npm run route:apply-edits -- <file>` bakes them into `public/data/` and bumps
the data version; it refuses an export made against a different route version.

## User points — device-local

Places Kevin adds himself, in IndexedDB under `userpoints.v1`.

```
schemaVersion, id, createdAt, updatedAt,
role: 'anchor' | 'waypoint',
type, title, notes, lat, lon,
onRoute: { alongKm, offRouteKm } | null,
classification: 'public' | 'private',
source: 'user', confidence: 'user-placed', verification, lastChecked
```

**Role decides behaviour.** An `anchor` is MOVED onto the route when saved, so
it can be a day finish without quietly adding distance to two days. A `waypoint`
keeps the position it was given and records how far off the line that is.

**`classification` is enforced, not advisory.** Lodging defaults to `private`
because a real booking is not repository content. `publicOnly()` filters every
export, and `tests/unit/userPoints.test.ts` asserts a private hotel appears in
neither the reference layer nor a day GPX while a public water point appears in
both.

User anchors are presented to the day planner in the same shape as shipped
anchors, so `#/plan` cannot tell the difference. `anchorAlongKm()` locates them
by projection rather than exact vertex match, because a snapped point sits
part-way along a segment rather than on a source vertex.

## Field captures

Written to IndexedDB store `captures`, exported as newline-delimited JSON so a
truncated file still yields every complete record before the break.

```
schemaVersion, id, createdAt (ISO), kind, text, dayId, waypointId,
lat, lon, accuracyM, externalRef, verifyLater, source
```

`kind` is one of `note`, `observation`, `question`, `safety-correction`,
`route-correction`, `photo-reference`, `voice-note-reference`.

`externalRef` is the join key to the primary record: a Voice Memo title, a photo
filename, a notebook page. There is no in-app audio recording, deliberately —
Voice Memos is better at it and the file belongs where the phone's backup can
see it. The shared timestamp is what later joins the mark, the track, the memo
and the photograph.

## Route import and export

### Importing a source route

Step one is done: `route-sources/kaidotrail-2026-08-20/` holds the **unmodified
original** plus `PROVENANCE.md` with its SHA-256, upstream commit, licence, and
a measured assessment of what is wrong with it. Never edit the original;
regenerate the derived files instead.

`scripts/import-kaidotrail.mjs` is source-specific. A general runtime importer —
GPX `<trk>`, multi-`<trk>`, `<trkseg>`, `<rte>`, and GeoJSON `LineString`,
`MultiLineString`, `FeatureCollection`, with visual review before adopting — is
Phase 2. It must:

1. Preserve the original file and a provenance sidecar **before** converting.
2. Keep separate tracks and segments separate. Never silently join disconnected
   geometry: that is precisely the mistake being designed against.
3. Preserve elevation where present, and not invent it where absent.
4. Refuse to assert pedestrian legality or safety.
5. Offer adoption as: new project · candidate replacement · prepared variant ·
   reference overlay · geometry for a named section.

### Exporting

`src/lib/routeExport.ts`, pure and tested.

**GPX for Footpath — one `<trk>` per continuous stretch, never several
`<trkseg>` in one track.** Measured on device 2026-08-20: Footpath bridges
multiple segments inside a track into one line, which on this route draws 21 km
across Ise Bay. It treats multiple `<trk>` elements as separate routes and
offers to save them as a named list, taking the list name from
`<metadata><name>` and each route name from `<trk><name>`. Names truncate around
25 characters in list rows, so front-load the discriminator.

Footpath also **ignores `<ele>` and substitutes its own terrain model**, so
elevation is not worth exporting and ascent should not be computed here at all.

**GeoJSON for an external editor.** `referenceLayerGeoJson()` emits anchors and
waypoints to load underneath while tracing in gpx.studio or CalTopo;
`activeRouteGeoJson()` emits the alignment itself, one LineString per stretch.

### Section export

`sectionGpx()` cuts the route between two anchors into a single-track GPX,
carrying the neighbouring anchors and nearby hazards as `<wpt>` context. One
track, never several — this is a section, not a route collection.

`sectionsByCoarseness()` ranks every adjacent-anchor pair by mean point spacing.
Pairs under 400 m apart are skipped; two anchors that close say nothing useful
about sampling.

### Licence obligation

The route is CC BY-SA 4.0 from 旧街道足跡マップ (kaidotrail). Anything derived
from it and published must carry the same licence, the attribution, and an
indication that changes were made. `route-meta.json` carries all three, the map
credit line shows it, the Route screen states it, and
`tests/build/bundle.test.ts` asserts the attribution survives into the bundle.

## Changing a schema

1. Bump the `schemaVersion` on the affected file.
2. Update the Zod schema and the TypeScript type together — the types are
   inferred, so they cannot drift.
3. Add a test for what the new version accepts *and* what it refuses.
4. For private data, add an explicit migration or refuse the old version with a
   message telling Kevin how to upgrade. Never silently coerce.
